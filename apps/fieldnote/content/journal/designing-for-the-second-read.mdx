Most interface reviews happen on the first read. Someone opens the screen, scans the hierarchy, and decides whether it feels right. That is a useful test, but it is not the only one.

A second read asks different questions. What happens when you already know where everything is? Can you still find the detail you came back for?

## Hierarchy is a promise

A heading tells you what a section is about. A subheading tells you how the section is organised. When those two levels disagree, the page becomes a small puzzle.

<Callout variant="warning" title="Watch for decoration">
  If a visual treatment only works on the first read, it is probably decoration.
  Structure should survive familiarity.
</Callout>

## Typography does the quiet work

The Supabase design system is a good reference here. Its type scale is deliberately narrow: a small number of sizes, used consistently, with generous line height and restrained weight changes.

That restraint is not minimalism for its own sake. It is what makes the second read possible. Nothing is competing for the surprise of the first impression.

## Make the return path obvious

Think about the last time you returned to a page you had already read. You probably remembered a phrase or a section heading, not the exact position. Search, anchors, and a visible table of contents are not navigation extras. They are the return path.

We try to give every long document:

- a stable heading hierarchy
- anchor links that work without JavaScript
- a table of contents that reflects the actual document
- metadata that stays useful after the publish date

## End with something usable

A good second read should leave the reader with a next action that is small enough to take. Not a call to arms. A link, a checklist, a file to open.

That is the standard we are aiming for.
